# ADR-002: Technical Result and Domain Result Separation

## Статус

Accepted

## Контекст

Action runtime выполняет PostgreSQL-функции и публикует их через HTTP API.

В системе существуют два разных типа результата:

1. Технический результат выполнения runtime.
2. Предметный результат операции.

Если смешать эти уровни, возникают проблемы:

- HTTP слой начинает зависеть от предметной модели;
- PostgreSQL-функции начинают знать о транспортных деталях;
- сложнее реализовать rollback при нарушении контракта;
- сложнее отличить ошибку выполнения от успешного бизнес-результата.

Например, создание платежной операции является предметным эффектом, а наличие `correlationId` или HTTP status code является техническим аспектом.

## Решение

Система разделяет технический и предметный результаты.

PostgreSQL target-функции возвращают только предметный результат.

Пример результата `payment.request`:

```json
{
  "operationId": "8c26513d-8441-43ea-b064-3bca8c240052",
  "requestId": "request-123",
  "operationKind": "PAYMENT_EXECUTION",
  "amount": "1000.00",
  "currency": "RUB",
  "status": "CREATED"
}
```

Runtime преобразует его в единый HTTP envelope:

```json
{
  "status": "ok",
  "outcome": "CREATED",
  "result": {
    "operationId": "8c26513d-8441-43ea-b064-3bca8c240052",
    "requestId": "request-123",
    "operationKind": "PAYMENT_EXECUTION",
    "amount": "1000.00",
    "currency": "RUB",
    "status": "CREATED"
  },
  "meta": {
    "correlationId": "1e534bdb-73a8-446a-a8f5-49c4959786c2",
    "actionVersion": 1
  }
}
```

## Ответственность PostgreSQL слоя

PostgreSQL target-функция отвечает за:

* изменение предметного состояния;
* создание operation;
* создание operation event;
* проверку предметных ограничений;
* возврат согласованного domain result.

PostgreSQL не отвечает за:

* HTTP status codes;
* JWT;
* correlation metadata;
* transport envelope.

## Ответственность Runtime слоя

Action runtime отвечает за:

* проверку JWT;
* построение server-side context;
* проверку request schema;
* выбор action из manifest;
* проверку policy;
* управление transaction boundary;
* проверку response schema;
* формирование HTTP envelope.

## Контроль контракта результата

Перед commit runtime проверяет:

* допустим ли outcome;
* соответствует ли result опубликованной response schema;
* является ли результат валидным JSON contract.

Если PostgreSQL-функция:

* возвращает неизвестный outcome;
* возвращает результат, не соответствующий schema;
* возвращает техническую ошибку вместо ожидаемого результата;

transaction откатывается.

Предметный эффект не считается успешным.

## Идемпотентность

Idempotency относится к runtime-уровню.

Runtime отвечает за:

* поиск предыдущего результата;
* проверку совпадения payload hash;
* возврат сохранённого результата;
* предотвращение повторного предметного эффекта.

При этом уникальность и конкурентность обеспечиваются PostgreSQL.

Process-local locks не используются.

## Последствия решения

### Положительные последствия

* PostgreSQL-функции остаются независимыми от HTTP;
* новые actions добавляются через manifest без изменения API;
* runtime имеет единый механизм обработки всех действий;
* rollback выполняется до публикации успешного результата;
* проще расширять систему новыми типами действий.

### Отрицательные последствия

* runtime должен выполнять дополнительную schema validation;
* необходимо поддерживать два уровня контрактов;
* ошибки контракта обнаруживаются только после выполнения target-функции.

## Рассмотренные альтернативы

### Альтернатива: возвращать HTTP envelope напрямую из PostgreSQL

Отклонено.

Причины:

* база начинает зависеть от транспорта;
* усложняется повторное использование функций;
* нарушается разделение ответственности.

### Альтернатива: каждый action реализовать отдельным C# controller

Отклонено.

Причины:

* новый action требует изменения исходного кода;
* нарушается database-first подход;
* невозможно публиковать неизвестные runtime actions без пересборки API.

### Альтернатива: доверять любому результату target-функции

Отклонено.

Причины:

* нарушается контракт response schema;
* возможно сохранение некорректного состояния;
* невозможен гарантированный rollback.
